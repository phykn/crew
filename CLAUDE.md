# crew

## Map

`src/backend/` is the Electron main process, in three layers that import only inward: `domain/` (pure rules and records) ← `app/` (use cases, and the ports they call the outside through) ← `adapters/` (SQLite, git, disk, Claude, MCP, Electron). `tests/architecture.test.ts` fails on an import that points outward, and on any Hangul in `src/backend`, `src/shared.ts`, or `src/preload.ts`: the main process keeps codes and keys (`Say`), and the window words them. `Chat` is the hub every use case reaches the others through (`chat.members`, `chat.runs`, `chat.tasks`, `chat.workflows`, `chat.wiki`, `chat.questions`, `chat.requests`, `chat.connections`). The part that changes the record announces it on the `changed` feed (a change to messages or tasks names its session), so the window and the interpreter's app actions take the same path and the window never reloads by hand.

`domain/` imports only itself, `src/shared.ts`, zod, xstate, and `node:path`:

- `records.ts`: every record type, snapshots and `changedFiles`, diffs, and a run's output (`skipped`, `NOT_HIRED`).
- `task.ts`: an XState machine says which status moves are allowed; the handback schema; which steps are satisfied, sent back, stuck, or skipped by a small change (`withoutPlan`).
- `workflow.ts`: `crew/workflows/*.json` steps (`after`, `verdict` + `rework` + `loops`, `requires`) and their validation.
- `policy.ts`: `checkCall` judges one tool call against a run's `Policy`: forbidden commands and writes outside scope are denied, and `writeTargets` reads what a shell command writes.
- `crew.ts`: `Crew` reads and checks the crew folder's contents (`CrewData`): `agents.json` (what each agent is for and the tools, write scope, skills, and MCP servers it starts with), each agent's instructions, rules, `mcp.json` (servers and their look-only tools), each skill's procedure, and the workflows; a copy (`temp`) is its original's key with the task and step after a dash (`baseKey`), runs on its definition, and is hidden once gone. The window hands over the names it shows at start (`useNames`): members' roles and starting nickname (`nicknameOf`, for a member the user has not named), workflow and step names (`workflows` fills steps nobody named), and approval modes; until then everything goes by its key. Only the user changes who holds what, in the window.
- `usage.ts`: a run keeps the running totals the SDK reported; `usage` counts each run's own share against the session's last report.
- `wiki.ts`: wiki documents, log lines, memories, and `[[title]]` links. `answers.ts`: the answer values allow, refuse, cancel.
- `providers.ts`: the connections the crew can run on, each its own service (the subscription by the computer's login, the API by a key); another joins this list with an adapter that runs the crew on it.

`app/` takes everything outside through `ports.ts`: the record (`Records`, one interface per kind), `Agent` (which also says whose account it runs on), `Secrets`, `Files`, `Versions`, `ToolServers`, and the `Feed`:

- `chat.ts`: the hub, and the user's conversation with the interpreter (one live run per session), projects, sessions (**New session** and `/clear` are the same call), and the approval mode.
- `requests.ts`: a member asks a colleague mid-step (`ask_peer`), as a thread in `requests` either side may continue; a busy peer or oneself is refused.
- `questions.ts`: answer cards under the interpreter's messages; a waiting run resumes when the user picks, and a card the interpreter's answer leaves open when it ends (as on a stop) is closed as cancel.
- `wiki.ts`: the project's `.crew` folder (made at start and when a project is added, and no agent may write it directly): the wiki, one file per document in `.crew/wiki/` with `index.md` and `log.md` kept by the app on each change (graph, change timeline), and each agent's memory, one file per agent at `.crew/memory/<key>.md` (a copy shares its original's), which `remember` rewrites whole; every run's prompt starts with its own memory and the wiki index, which a resumed Claude session is sent again only once they change (`Runs.contexts`), so the system prompt stays cached.
- `librarian.ts`: the librarian keeps the wiki on its own, one run at a time per project: after a task ends (done or failed), and at start for commits made since it last looked (a project seen first only marks HEAD).
- `members.ts`: a project's members: effective `Settings` (definition overlaid with the user's `config`), permission and skill changes (recorded by name only), `update` (the one way the window and the interpreter change a nickname, model, or hiring; `KEPT` members cannot be let go), `reset` (back to the shipped nickname and model, hired, and no permission changes), and `fire` (idempotent; a member at work leaves after its run).
- `runs.ts`: every run: one lane per member and session, the `Policy` and guard each run gets, and write reservations; `ask` answers a side question from a forked copy of a member's session, beside its lane, that can only read (its run is marked `side`); `spend` is a session's cost per member and model, for the window and the interpreter alike.
- `guard.ts`: every non-read-only tool call goes through `checkCall`; denials are logged, a tool outside the role is asked on a card (kept for that task), allowed in `auto` mode, and nothing is checked in `bypass`.
- `locks.ts`: write reservations by real path per task; overlapping writes wait, and a file changed while waiting is refused once so it is read again; every path a task reserved is kept (`touched`) to tell its writes from anyone else's.
- `tasks.ts`: a task the interpreter opens starts with the conductor's assign step (`open`), whose answer sets its kind, size, and lone member (`settle`), and ends with the conductor's judge step once every step holds (`judged`: done, a rework with points, a re-plan, or a failure), which also takes new words and a stuck task when there is no plan; `Tasks.drive` runs the ready steps in parallel until every step is satisfied, stops a step past its loop limit or a redo that changed nothing, and tells the interpreter the report (each step's outcome without its body; the librarian gets the full one). A member whose Claude session already read this task is sent only what is new (`seenBy`), and a retry only what went wrong. A failed run is retried after a wait (`retryWaits`). A small change, or one given to a member who writes the project, skips the plan; one given to anyone else is one step. A member already at work in the session, or given two steps at once, works through a copy that leaves when the task ends; a task past its loop limit goes back to the conductor's plan step once (`replan`), with its loop counts started over. A making step's change version is what differs from the task's baseline, git or not, kept to the files under paths the task reserved (`ownChanges`) unless it reserved none or was cut by a restart.
- `connections.ts`: the app-wide connections the Connect tab shows, the one in use (the subscription until the API is picked, which needs its saved key), the key a run goes with, and a check of whose account answers.
- `workflows.ts`: a project's saved workflow versions override the shipped ones; `Workflows.save` validates, refuses a stale base, applies by scope, and keeps the reason with the version.

`adapters/` implement the ports, or call the use cases from outside:

- `sqlite/`: `store.ts` (`Store` implements every record port with `node:sqlite`; a message's pictures sit in their own table, `message_images`) and `migrations.ts` (schema changes are appended to `MIGRATIONS`, never edited in place).
- `git/versions.ts`: in a git repository `mark` commits the folder at a task's start and at each version under `refs/crew/task-N/` (a copied index and `commit-tree`, so the user's branch, HEAD, index, and hooks are untouched); `diff` reads a version's own files against the start, and `forget` drops the refs with the session.
- `files/`: `files.ts` (content-hash snapshots, real paths, and output folders) and `crew.ts` (`loadCrew` reads the shipped crew folder).
- `claude/`: `agent.ts` (one run through the Claude Agent SDK, with an inbox for messages said mid-run; a run never throws, so an SDK that fails to load is a failed run; a run on the API carries its key as `ANTHROPIC_API_KEY` and a run on the subscription drops any it inherited, and a check asks Anthropic about a key or Claude Code about its login and plan) and `script.ts` (when `CREW_SCRIPT` names a JSON script, the crew answers from it instead of Claude, for window tests).
- `mcp/`: the in-process MCP servers (`servers.ts` makes them per run): `secretary.ts` (the interpreter's `start_task`, which hands the conductor the request only, `ask_user`, `reopen_task`, `reassign`, workflow, and `ask_member` tools), `member.ts` (`ask_peer`, and the conductor's `ask_user` card), `wiki.ts` (`wiki_read`/`remember` for everyone and `wiki_write`/`wiki_delete` for the librarian alone, loaded from the first turn rather than behind tool search), and `app.ts` (the interpreter's `app` server and its `help/`: every window action in one catalog, found with `app_find_actions` and done with `app_read`/`app_act`; changes to mode, a regular's hiring, and deletions ask the user on a card, and permissions are left to the user's window; `OFF_CATALOG` says why a window call is left out, and a test keeps the two in step; screens move through the `navigate` feed).
- `electron/`: `secrets.ts` (saved keys, encrypted with `safeStorage` in the record's settings), `ipc.ts` (every call the window can make, each with a Zod schema its arguments are typed from), `camp.ts` (what the camp shows: who works on what, and record lines that play as scenes, read from each line's kind, status, and detail rather than its wording), and `window.ts` (the window never navigates, so a file dropped outside the chat input cannot replace the app; sent pictures are served at `crew-image://message/<id>/<n>?at=<sent time>`, since ids of deleted messages are given again, so the message list carries only their count; the `notify` feed goes to the window, which words it and hands it back through `window.notify` to show as a system notification while the window is not focused, and the `busy` feed keeps the computer from sleeping while any run is at work).

`wire.ts` puts the app together from the real adapters (tests use it too), `start.ts` adds the record, the crew folder, and the window, and `index.ts` only reads where those are (the record file is `CREW_DB` or `userData/crew.db`) and calls `start`.

`src/preload.ts` exposes `window.crew.call` and `window.crew.on` (the `changed`, `stream`, `navigate`, and `notify` feeds). Both sides use `src/shared.ts` (approval modes, models and each member's starting model, the shape of the names the window hands over, the statuses of a task at work).

`src/frontend/` is the React window:

- `api.ts` types calls from the main handlers, and `follow` rereads a screen's data on each change, dropping a reply that lands after the screen moved to another session or project; `workspace.ts` holds the project, session, and crew the window shows; `time.ts` reads the record's UTC times in the user's time zone; `stick.ts` glides the chat and the log to their bottom as they grow while the user is there (a jump under reduced motion); every word on screen is a key, worded by `t()` in `lang.ts` from `ko.ts` and `en.ts` (the same keys, which tsc holds in step; `{name}` fills in a value and `{name|을}` adds the Korean particle `korean.ts` picks), in the language the title bar's toggle picks and the record keeps (`lang.read`, `lang.write`); `locale.ts` words every code the main process sends (`say`) and builds the names handed over at start and on each language change (`names`); `tokens.css`, `ui/`, and `styles.css` are the design system below; `Gallery.tsx` is the parts gallery.
- `components/`: `TitleBar.tsx` (the drawn title bar with the version, and the language toggle beside the window buttons), `Chat.tsx` (messages, answer cards, slash commands, approval mode, attached pictures, and messages held with Ctrl+Enter until the interpreter is done, which live only in the window), `TaskCards.tsx`, `Log.tsx`, `Connections.tsx` (the Connect tab), `Changes.tsx` (one file's diff in a popup, opened from a file name in the log when git kept that version; the crew works on while it is open), `Memory.tsx` and `WikiGraph.tsx`, `WorkflowView.tsx` (React Flow editor; node positions save as the layout), `Legend.tsx` and `Permissions.tsx`, `ProjectBar.tsx` and `ProjectTree.tsx`, `Icons.tsx` (kit and tab icons).
- `camp/`: the camp, drawn with PixiJS (WebGL) and GSAP: `walkers.js` moves people in plain JS (the crew the app opens with walks in from beyond every edge; they speed up and slow down, and sit on the free rugs round the fire), `figure.js` holds a person's size and head height, `palette.js` holds its colors, and `art/` paints ground, props, and people once: `props.js` builds each prop from solids that `solids.js` ray-marches through the camp's projection (toon shades per material and the fire's and torches' warmth; shadows on the ground are the light map's alone), `figures.js` paints each role's figure from `people/<role>.js` (letter pictures `graphics/characters/trace.py` makes from the approved sheets, one pose per motion, with the fire's warmth on the side toward it), and `finish.js` refines what props bake (rim light, grain); `stage/` turns those into textures (`bake.ts`) and draws the scene each frame (`scene.ts`): `light.ts` (a light map multiplied over the scene, and soft blurred shadows on the ground for everything that blocks a flame), `people.ts` (each person's pose and frame: walking by ground covered, casting's start, loop, and end, a blink now and then, and the firelit copy), `labels.ts`, and `effects.ts` (flames, sparks, smoke); `components/Camp.tsx` holds the `<Application>` and feeds it the crew and `camp.state` (the first read for each session is only a baseline, so neither a late camp nor a session switch replays history). The window forbids eval, so Pixi loads `pixi.js/unsafe-eval`.

Elsewhere:

- `crew/`: the crew as parts that would work under another app too, in English: rules, agents, skills, MCP servers, and workflows. What only this app shows lives outside it, in the window: roles, starting nicknames, workflow and step names, approval mode names, and skill labels in `src/frontend/ko.ts` and `en.ts`, and each member's name tag color and each skill's icon in `src/frontend/crew.ts`; starting models are in `src/shared.ts` (`MEMBERS`).
- `graphics/`: working files for drawing the camp, which the app never loads: one folder per thing under `props/`, `ground/`, `effects/`, and `characters/`, each a `brief.md` and its final pictures, and `preview.html`, which paints props with the app's own code (see its README).
- `docs/agents.md`: the crew's design: each agent's jobs, what it takes and gives, its skills, write scope, and starting model, the workflows, and the rules, memory, and wiki they follow.
- `tests/`: Vitest with a fake SDK (`npm test`), one file per module in folders that mirror `src/backend` (`domain/`, `app/`, `adapters/`); `tests/support.ts` holds the shared setup (`openChat`, `reopenChat`, the scripted crew); `tests/live/` calls real Claude (`npm run test:live`).
- `e2e/`: Playwright Electron tests; they run on the packaged build (`npm run test:e2e`).
- `demo/`: the README's GIF (`npm run demo`): `record.spec.ts` plays a scripted task in the app and keeps Chrome's screencast frames (a scripted turn's `wait` makes the crew visibly work), `make.mjs` cuts them into scenes, and `video/index.html` is the HyperFrames composition that adds the captions and camera.

## Design system

The window is drawn in three layers, each using only the one under it:

1. Tokens, `src/frontend/tokens.css`: the palette (`--wood-700`: a hue and a step), then roles named `--{role}-{target}-{state}` (`--surface-sheet`, `--text-muted`, `--action-primary-bg-hover`), and the scales (`--sp-*`, `--fs-*` in five steps, `--r*` in three, control heights `--h-sm`/`--h-md`/`--h-lg`). Only roles point at the palette.
2. Parts, `src/frontend/ui/`: `Button` (`variant` secondary, primary, quiet, row, link; `tone` danger, muted; `size`, only the type size for row and link; `iconOnly`, `pressed`, `dirty`, `wrap` for words of any length), `Segmented` (`size`), `Choice` and `ChoiceTrigger`, `Menu` (`SelectMenu`, `SelectItem`, `ListMenu`), `Field` (`Input`, `TextArea`, `Label`, `Checkbox`, `FileInput`), `Tabs` (`TabList`, `Tab`, `TabPanel`), `Fold`, `Switch`, `Chip`, `Badge` (`tone`), `Dialog` (`DialogHead`, `DialogTitle`, `DialogActions`, `DialogClose`), `Confirm` (the one question before a removal or a loss), `Toolbar`, `Empty`. Each has its CSS beside it under `.ui-*` classes, with one hover, pressed, disabled, and focus look.
3. Screens, `components/` and `styles.css`: layout and what only that screen has. A screen passes its own class for placement (position, layout size, gaps) but never restyles a part: color, background, border, padding, font, and underline are the part's.

A new screen picks parts first; a look no part has becomes a variant of one, shown in the gallery, before any screen uses it. `tests/frontend/styles.test.ts` fails on a palette token, raw color, or pixel number outside `tokens.css`, on a raw `<button>`, `<input>`, `<textarea>`, `<label>`, or `<details>` or a Radix dialog, switch, or tabs in a screen, on a `.ui-` selector in `styles.css`, on a look property set on a class a screen hands a part, and on extra size steps. The gallery (`Gallery.tsx`, opened only when started with `CREW_GALLERY=1`) shows every part and token; `e2e/gallery.spec.ts` compares it with baseline images, refreshed with `--update-snapshots` when a part changes on purpose.

## Rules

- A bug-fix and refactor plan is in `docs/groove/PLAN.md` (local, not in git); a session continuing it uses groove to do its first unchecked task.
- Prompts, code, and comments are written in English; on-screen text is Korean or English, from `ko.ts` and `en.ts` only (`tests/frontend/words.test.ts` fails on Hangul anywhere else in `src/frontend` but the gallery).
- Comments say only why, in one line.
- Git: commit on main and push to GitHub by URL (`git push https://github.com/phykn/crew main`); pull the same way; add no remote and never force-push. The hooks in `scripts/hooks` (`core.hooksPath`) bump the version in `scripts/version.mjs` on each commit.
- Tests never touch the real record: point `CREW_DB` at a scratch file.
- Shells opened by editors may set `ELECTRON_RUN_AS_NODE=1`; unset it before starting Electron.
